# WHICH-105 — 사용자 질문 게시·대기 관리

작성일: 2026-08-30
상태: 게시·대기 관리 + 검사 입력 결합 + 로컬 OCR/QR 실검사 + 공개 준비 진단 구현, 전체 출시 승인 전

## 이번에 연결한 흐름

| 경로                  | 게시 조건                                                           | 사용자 결과                                 |
| --------------------- | ------------------------------------------------------------------- | ------------------------------------------- |
| 텍스트                | 기존 텍스트 안전 규칙 및 작성 한도 통과                             | 즉시 게시, 내 질문 기록                     |
| 승인 Library          | 현재 게시 가능한 A/B 쌍, 권리·만료·회수 재확인                      | 즉시 게시, 출처·alt·crop 연결               |
| 직접 업로드           | 기존 capability·가입 동의·업로드 세션·한도 통과                     | 비공개 제출, 수정·취소·대안 선택            |
| 직접 업로드 검수 완료 | 현재 A/B가 모두 READY / APPROVED / PUBLISHED이고 작성자가 활성 상태 | 현재 수정본의 텍스트 재검증 후 한 번만 게시 |

마지막 행은 **명시적 검수 승인 후의 게시 연결**이다. Shadow 점수나 탐지 실패를 승인으로 취급하지 않는다. 로컬 OCR/QR 실검사는 아래 3차 범위로 연결했지만, 저위험 자동 판정의 실행부와 WHICH-111 운영 승인까지 완료된 것은 아니다. 기존 OFF/PILOT 및 kill switch 설정을 바꾸지 않았다.

## 사용자 화면

- Web: `/me` → 내 질문 → `/me/submissions`. PC와 모바일 웹이 동일한 반응형 화면을 사용한다.
- 업로드 제출 완료 시 이 화면으로 이동한다.
- 네이티브 앱: 작성 화면 하단의 최근 제출 목록에서 동일한 전환 API를 사용한다.
- 처리 중/수정 필요 질문: 수정·A/B 이미지 교체, 이미지 없이 게시, 승인 Library 선택 후 게시, 상태 확인, 제출 취소.
- 게시된 질문: 질문 링크. 취소된 질문: 변경 버튼 없음.
- 기존 `/me/moderation`의 중복 업로드·개별 권리 확인 폼은 내 질문 링크로 통합한다. 제품 재검토 및 권리 요청 기능은 유지한다.
- 완료/실패 피드백은 toast, 게시·취소·정책 재검증 결과는 기존 알림함에 기록한다.
- 신규 즉시 게시도 제출 기록을 남긴다. 적용 전 즉시 게시된 질문의 일괄 과거 기록 이관은 이번 범위에 포함하지 않는다.

## 상태와 데이터

- migration `0052`: 제출 status에 `CANCELLED`, 게시 Issue FK `published_issue_id` 추가. 기존 레코드는 null로 유지한다.
- 기존 `status`와 별도로 응답에 `publicationState`를 반환한다: PROCESSING / PUBLISHED / NEEDS_CHANGES / REJECTED / QUARANTINED / CANCELLED.
- 자산 거절·삭제·격리 상태를 합성해 표시하되, 게시 여부는 `publishedIssueId`로 구분한다.
- 수정과 전환은 수정본을 추가한다. 과거 이미지와 본문 이력은 덮어쓰지 않는다. Library 게시 시 최종 이미지·권리 연결은 issue snapshot 및 Library usage에 남는다.
- 취소는 제출 종료이며 R2 원본 영구 삭제와 다르다. 비공개 파일은 기존 보관·고아 자산 정리 정책 대상이다.

## API

`POST /v1/member/issue-submissions/:submissionId/actions`

```json
{ "expectedRevision": 2, "action": "TEXT_ONLY" }
```

- `action`: TEXT_ONLY / LIBRARY / CANCEL / CHECK. LIBRARY는 `libraryPairId` 필수.
- 소유자 세션, 현재 수정본, 변경 가능한 비공개 상태를 검증한다.
- 제출 advisory lock + 행 잠금 + 단일 트랜잭션으로 중복 게시와 전환 경합을 막는다.
- 동일한 완료 요청 재시도는 현재 상태를 반환한다. 게시된 제출에 취소 요청을 보내도 기존 게시글을 삭제하지 않는다.
- 직접 업로드 ID를 즉시 게시 API에 넣는 우회는 거절한다.
- 2026-09-01부터 텍스트·Library 질문과 이미지 비공개 제출에 24시간 작성 횟수 한도를 두지 않는다.
  중복 요청 방지, 제출 소유권·revision 검증, 취소 상태 보호와 이미지 안전 검사는 유지한다.
- 과거 수정본/취소/게시된 제출을 대상으로 한 지연 moderation 작업은 stale로 처리한다.
- Web BFF는 쿠키+Origin 검증, Mobile BFF는 Bearer 검증. 본인 제출만 조회한다.

## 배포·롤백

1. API migration 적용 후 API/Web을 배포한다. 새 필드는 추가형이다.
2. 운영 테스트는 별도의 허용된 계정으로 제출 → 수정 → 텍스트 전환, Library 전환, 직접 이미지 승인 → 게시, 취소 → 승인해도 미게시를 확인한다.
3. creator 기능이 꺼져 있으면 승인 이벤트의 제출 자동 연결도 꺼진다. 직접 이미지 자동 안전 공개 설정은 별도로 유지한다.
4. 롤백 시 새 컬럼/이력은 삭제하지 않는다. CANCELLED 상태를 모르는 구버전 mutation 코드로 되돌리면 취소 의미가 깨질 수 있으므로 writer와 승인 연결을 먼저 비활성화한다.

## 후속 완료 기준

### 2026-08-30 검사 입력 결합 보강

- 제출 `ISSUE_VERSION` 검사는 해당 `member_issue_submission_revisions`의 질문·설명·A/B 선택지와 두 이미지를 하나의 요청으로 검사한다. 수정/이미지 교체는 새 수정본과 hash의 별도 검사다.
- 업로드 직후 `ISSUE_MEDIA_ASSET` 검사는 이미지 단독 검사다. 이미지에 연결된 임의의 과거/현재 질문 문맥을 찾지 않는다. 제출 전체 검사와 혼동하지 않는다.
- 각 이미지는 불변 asset version 1의 정규화 SHA-256과 실제 읽은 WebP 바이트를 대조한 후 1024px 이하 메타데이터 제거 파생본으로 전달한다. A/B 순서와 기존 자동 alt/CONTAIN 의미를 유지하며, 추가 사용자 입력을 요구하지 않는다.
- 캐시 키는 `which-provider-input-v2 + targetType + normalizedInputHash`로 분리한다. 문맥이 섞일 수 있는 구 캐시는 재사용하지 않는다. 같은 계약·동일 입력의 유효 캐시만 재사용하고 만료 항목은 갱신한다.
- 완료 저장 직전에 수정본·hash·종료 상태·이미지 상태를 잠금 안에서 다시 확인한다. 검사 중 수정/취소/격리 또는 lease 상실 시 결과를 현재 근거/캐시에 반영하지 않는다.
- 결과에는 `inputScope`, `imageCount`, `inputBinding`을 남긴다. `SUBMISSION_REVISION`의 두 이미지 합산 결과는 특정 A/B 이미지에 대한 개별 판정으로 복사하지 않는다. 원문·픽셀·원본 Provider response는 저장하지 않는다.
- 입력 불일치/파일 없음/해시 불일치/권리 문제/불완전 Provider 응답은 실패 또는 SKIPPED이며, 승인으로 간주하지 않는다. 모델 snapshot은 기존 `omni-moderation-2024-09-26`을 유지한다.
- 캐시에 남기지 못한 지연 결과·실패도 검사 시도 감사 이벤트로 집계한다. v2 캐시와 중복 합산하지 않는다. 이 집계는 다중 worker의 원자적 예산 예약을 구현했다는 뜻은 아니며, 자동 공개 전 예산 동시성 검증은 여전히 필요하다.
- 기존 Render 키 재사용만 승인되었다. 새 키 발급, 로컬 키 복사, 운영 이미지 외부 전송 테스트, Provider/자동 공개 활성화는 실행하지 않았다. DB migration은 추가하지 않는다.

### 2026-08-30 로컬 OCR·QR·바코드 실검사

- 서버 내부 Tesseract.js 한국어/영어 OCR 및 ZXing QR/바코드 검사를 정규화 WebP 업로드 경로에 연결했다. 추가 외부 API 호출 없이 로컬에 설치된 언어 데이터/WASM을 사용한다.
- OCR 원문·QR/바코드 내용은 버리고 개인정보 후보 분류 및 검사 상태만 기록한다. 실제 픽셀 테스트와 업로드 통합 테스트로 비공개 유지·원문 미저장을 확인한다.
- 이미지 크기·해상도, 자식 프로세스 실행 시간, API 프로세스당 동시 검사 1개, 출력 스키마를 제한한다. timeout/crash/malformed/busy는 검사 미완료이며 승인으로 처리하지 않는다.
- 기본값 `ISSUE_MEDIA_LOCAL_SCANNER_MODE=OFF`. Render 환경변수 및 자동 공개 설정은 변경하지 않았다. 실제 호스트 CPU/RSS 검증 후 별도 활성화한다. JS heap 제한은 전체 메모리 제한이 아니다.
- 얼굴·신분증·스크린샷 시각 검사는 여전히 미지원이다. 깨끗한 OCR/QR 결과만으로 자동 공개하지 않는다. 상세 계약과 배포/롤백 절차는 [로컬 검사 운영 문서](./issue-media-rule-signal-gate.md)를 따른다.

### 2026-08-30 제출별 공개 준비 진단·근거 계약 보강

- 현재 제출과 A/B 이미지·로컬 규칙·Provider 지원 범위를 검사 완료 기록의 `publicationReadiness`에 연결했다. 수정/취소/격리로 오래된 결과는 현재 근거에 반영하지 않는다.
- `diagnose-publication <submission-id>`로 최신 Run과 현재 상태를 읽기 전용 재조회할 수 있다. 원문·이미지·OCR 내용은 반환하지 않고 외부 API를 호출하지 않는다.
- 낮은 위험 점수, OCR/QR 완료, 캐시 적중만으로 전체 안전 검사 통과를 만들지 않는다. 텍스트 전용 카테고리는 이미지 검사 완료로 취급하지 않는다.
- PROVISIONAL 판정은 필수 검사별 hash/정책/버전/유효기한 결합 근거를 요구하며 누락·중복·충돌 근거를 거절한다. 현재 Shadow는 이 근거를 발급하거나 공개를 실행하지 않는다.
- 추가 유료 Provider·새 키·운영 플래그 변경·DB migration 없음. 상세 한계와 명령은 [공개 준비 진단 문서](./issue-media-publication-readiness.md)를 따른다.

### 2026-08-30 OCR 본문 안전 검사 연결

- 기존 로컬 scanner의 별도 일시 IPC 경로에서 최소화된 OCR을 얻어 질문·A/B 이미지의 기존 단일 Provider 요청에 결합한다. 사용자 입력 폼은 추가하지 않는다.
- 개인정보 후보는 OCR 전체 전달을 보류하고 실패/부분 추출/잘림은 완전 검사로 인정하지 않는다. Run/캐시에는 hash·상태·글자 수만 남긴다.
- OCR mode/계약/engine profile로 캐시를 분리하고 LOCAL의 미완료 결과는 재사용하지 않는다. 실제 픽셀·mock Provider·로컬 DB로 검사 결합과 비공개 유지를 검증한다.
- 새 키·유료 모델·추가 API 호출·migration·운영 설정 변경 없음. 상세 내용과 한계는 [이미지 속 텍스트 안전 검사](./issue-media-embedded-text-safety.md)에 기록한다.

전체 완료까지 다음 항목은 계속 남아 있다.

2026-08-30: [근거 해석기·결정 엔진 연결](./issue-media-publication-evidence.md)을 추가했다.
현재 제출/이미지/규칙 근거와 계정/권한/동의를 다시 읽어 검사별 상태를 구성한다.
원문이나 Provider 캐시에 결정 근거를 복사하지 않으며 자동 공개 실행은 여전히 미연결이다.

- WHICH-103 결정 엔진 → 공개 실행부 연결: 최신 revision/hash, 현재 capability/consent, 유효한 신호와 예산·privacy/release gate를 같은 결정에서 확인.
- 구현된 로컬 OCR/QR의 실제 호스트 자원·정확도·동시 요청 검증 및 미지원 시각 검사 보완. 실패를 저위험으로 간주하지 않음.
- WHICH-111 smoke/shadow 증빙 및 활성화 승인. 직접 업로드의 정상 저위험 자동 공개, 애매한 결과만 사람 검토로 보내는 최종 목표는 유지한다.
- 실제 R2/운영 계정 및 네이티브 기기의 E2E 확인. 이번 자동 테스트는 로컬 DB 및 mock 경로이며 운영 업로드 증빙을 대신하지 않는다.

따라서 WHICH-105는 전체 AC가 충족될 때까지 Doing으로 유지한다.
