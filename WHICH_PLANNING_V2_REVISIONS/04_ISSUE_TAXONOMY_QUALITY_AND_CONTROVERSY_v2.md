# 1. 문서의 역할과 핵심 목표

## 1.1 왜 별도 분류 체계가 필요한가

WHICH에서 카테고리는 단순 탐색 메뉴가 아니다. 하나의 Issue 분류 결과가 다음 시스템의 공통 입력이 된다.

- 신규 사용자 관심사 온보딩
- 외부 자료 수집과 편집 캘린더
- Issue Pool 재고 계획
- 추천 후보 생성과 ML Feature
- 피드 다양성 Re-ranking
- 정치·고위험 콘텐츠 분기
- 댓글·투표 권한 정책
- 모더레이션 Queue 우선순위
- 성과·안전·품질 분석
- 사용자 설정과 `이 주제 덜 보기`

분류가 흔들리면 추천과 운영이 서로 다른 언어를 사용하게 된다. 예를 들어 같은 AI 규제 질문을 어떤 팀은 `IT·테크`, 다른 팀은 `사회`, 또 다른 팀은 `정치`로 다루면 다음 문제가 생긴다.

- 관심사 추천이 일관되지 않는다.
- 정치 Safe Line이 우회될 수 있다.
- 카테고리별 재고가 왜곡된다.
- 모델 학습 Label이 불안정해진다.
- 신고율과 품질 지표를 비교할 수 없다.

## 1.2 한 줄 목표

> 각 Issue를 사용자의 관심 영역, 소비 경험, 질문 구조, 위험도와 신뢰 요건으로 일관되게 분류하고, 유희성은 높이되 질문의 대등성·안전·대표성 원칙을 훼손하지 않는 게시 기준을 제공한다.

## 1.3 이 문서가 답해야 하는 질문

- 이 질문은 어느 카테고리에 속하는가?
- 사용자에게 어떤 종류의 경험을 제공하는가?
- 출시 초기의 가벼운 질문으로 적합한가?
- A/B 두 선택지만으로 의미를 보존할 수 있는가?
- 어느 Risk Level과 민감 플래그를 가져야 하는가?
- 출처와 배경이 필요한가?
- 질문과 선택지는 중립적이고 대등한가?
- 기존 Issue와 중복되는가?
- `논쟁` 피드에 들어갈 만큼 접전이고 표본이 충분한가?
- 추천 시스템이 어떤 Feature와 제한을 적용해야 하는가?

## 1.4 성공 조건

이 문서는 다음 상태가 되면 운영 가능한 기준선으로 본다.

1. 동일한 샘플 Issue를 서로 다른 운영자가 유사하게 분류한다.
2. 정치·선거 경계 사례가 일반 큐로 누출되지 않는다.
3. 유희형 질문이 자극성·모욕성 질문으로 변질되지 않는다.
4. 50:50에 가깝다는 이유만으로 저표본 Issue가 논쟁 상위에 오르지 않는다.
5. 추천·온보딩·분석에서 동일한 코드와 버전을 사용한다.
6. 분류 변경과 점수 변경을 Audit할 수 있다.

# 2. 핵심 설계 원칙

## 2.1 카테고리와 위험도는 분리한다

**[확정]** 카테고리는 `무엇에 관한 질문인가`를 설명하고, Risk Level은 `어떤 피해와 조작 위험이 있는가`를 설명한다.

```text
Category = IT·테크
Risk = LOW
예: 스마트폰은 작은 화면과 큰 화면 중 무엇이 더 좋은가?

Category = IT·테크
Risk = HIGH
예: 특정 기업의 보안 사고 책임을 개인 임원에게 물어야 하는가?

Category = IT·테크
Risk = RESTRICTED 후보
예: 선거 기간 생성형 AI 규제를 특정 정당이 추진해야 하는가?
```

카테고리만 보고 Risk를 자동 확정하지 않는다.

## 2.2 한 Issue를 여러 축으로 분류한다

**[확정]** 하나의 `primary_category`만으로 제품 전체를 설명하지 않는다.

```text
Domain Category
+ Subcategory
+ Topic
+ Experience Mode
+ Lifecycle Type
+ Question Archetype
+ Risk Level
+ Sensitivity Flags
+ Source Requirement
+ Geography / Language
```

각 축은 서로 다른 목적을 가진다.

## 2.3 초기에는 유희와 즉시 선택 가능성을 우선한다

**[확정]** 출시 초기 Issue Pool과 신규 사용자의 첫 피드는 생활 취향, 음식, 문화, 게임, 무해한 가상 선택, 가벼운 관계 딜레마 등 **인지 비용이 낮고 답하는 재미가 있는 질문**을 중심으로 구성한다.

유희성의 목적은 다음과 같다.

- 사용자가 WHICH의 `질문 → 선택 → 결과` 보상 구조를 빠르게 이해한다.
- 가입이나 배경 지식 없이 첫 투표를 완료한다.
- 한 세션에서 여러 질문을 자연스럽게 소비한다.
- 친구와 결과를 비교하거나 공유할 동기를 만든다.
- 고위험 갈등 소재 없이도 참여 밀도를 확보한다.

유희성은 선정성·모욕성·허위 전제와 동일하지 않다.

## 2.4 품질과 안전은 Engagement보다 먼저 판정한다

```text
Quality / Safety Eligibility
→ Candidate Ranking
→ Diversity / Risk Re-ranking
→ Final Feed
```

**[금지]** 반응률이 높을 것이라는 이유로 Hard Gate를 통과하지 못한 질문을 게시하거나 추천하지 않는다.

## 2.5 하나의 Issue에는 하나의 주 판단 축을 둔다

질문 하나에 생산성, 행복, 비용, 공정성 등 여러 판단 축을 동시에 넣지 않는다.

```text
나쁜 예
재택근무는 생산성을 높이고 삶의 질도 개선하므로 전면 확대해야 할까?
```

위 문장은 최소 세 개의 판단을 포함한다.

## 2.6 질문과 선택지의 의미는 첫 정상 투표 후 고정한다

첫 정상 투표 이후 질문 또는 A/B 의미를 변경하면 기존 결과와 신규 결과를 함께 해석할 수 없다. 의미 변경이 필요하면 기존 Issue를 종료하고 Successor Issue를 만든다.

## 2.7 정치·선거는 애매하면 강하게 분류한다

**[확정]** 정치인, 정당, 선거, 후보, 캠페인, 현직 정부에 대한 지지·반대와 직접 연결되는 질문은 `RESTRICTED`로 분류한다.

경계가 불명확하면 일반 큐가 아니라 정치 검토 큐로 보낸다.

## 2.8 논쟁은 분노가 아니라 접전이다

**[확정]** WHICH의 `논쟁`은 A/B 정상 투표 분포가 50:50에 가까운 Issue를 의미한다.

- 댓글 공격성
- 신고 수
- 분노 표현
- 외부 커뮤니티 충돌

은 논쟁 여부를 정의하는 주 신호가 아니다.

## 2.9 논쟁 피드에서도 투표 전 정확한 결과를 숨긴다

**[설계 기준]** 사용자가 아직 참여하지 않은 Issue에는 `초접전`, `접전 중`과 같은 방향 중립적 상태만 표시하고, 정확한 A/B 비율은 투표 후 공개한다.

정확한 결과를 사전에 보여주면 `결과가 궁금해서 투표하는 보상`과 독립 판단 원칙이 약해진다.

## 2.10 코드와 표시 문구를 분리한다

내부 코드는 안정적으로 유지하고 사용자에게 보이는 라벨은 개선할 수 있다.

```text
Internal Code: WORK_CAREER
Display Label: 직장·커리어
```

카테고리 명칭을 바꾸더라도 과거 이벤트와 모델 Feature가 깨지지 않게 한다.

# 3. 다축 Taxonomy 모델

## 3.1 필수 분류 축

| 축 | 필수 여부 | 값의 수 | 주요 사용처 |
|---|---:|---:|---|
| `primary_category` | 필수 | 1 | 탐색, 다양성, 분석 |
| `subcategory` | 필수 | 1 | 관심사·후보 검색·운영 |
| `secondary_categories` | 선택 | 0~2 | 교차 주제 검색 |
| `topics` | 필수 | 1~5 | 세밀한 추천·온보딩 확장 |
| `experience_mode` | 필수 | 1 | 첫 세션 믹스·유희성·UX |
| `lifecycle_type` | 필수 | 1 | Evergreen·Current·Trend 운영 |
| `question_archetype` | 필수 | 1 | Binary Fit·문장 검수 |
| `risk_level` | 필수 | 1 | 권한·검수·노출 정책 |
| `sensitivity_flags` | 선택 | 0개 이상 | Risk 상승·모더레이션 |
| `source_requirement` | 필수 | 1 | 출처 요건 |
| `geography` | 필수 | 1개 이상 | 지역 맥락·추천 |
| `language` | 필수 | 1 | 문장·추천·운영 |
| `entities` | 선택 | 0개 이상 | 인물·기관·제품·사건 추적 |
| `taxonomy_version` | 필수 | 1 | 재현성과 분석 |

## 3.2 분류 예시

```yaml
issue_id: ISS-20260817-00123
primary_category: LIFE
subcategory: FOOD
secondary_categories: [CULTURE_ENT]
topics: [DELIVERY_FOOD, PRICE_VALUE]
experience_mode: PLAYFUL_QUICK
lifecycle_type: EVERGREEN
question_archetype: OPTION_PAIR
risk_level: LOW
sensitivity_flags: []
source_requirement: NONE_REQUIRED
geography: [KR]
language: ko
entities: []
taxonomy_version: taxonomy_v2.0
```

## 3.3 Primary Category 선택 규칙

Primary Category는 다음 순서로 결정한다.

1. 사용자가 실제로 판단하는 대상이 무엇인가?
2. 질문을 이해하는 데 가장 중요한 맥락은 무엇인가?
3. 추천에서 어떤 관심사와 연결하는 것이 자연스러운가?
4. 어느 운영팀이 기본 책임을 가져야 하는가?

단순히 본문에 특정 단어가 등장한다는 이유로 카테고리를 정하지 않는다.

예:

```text
회사에서 생성형 AI를 사용해도 될까?
```

- 판단 대상이 업무 정책이면 `WORK_CAREER / WORKPLACE_POLICY`
- 기술 기능 자체를 비교하면 `TECH / AI`
- 법적·공공 규제면 `POLITICS_PUBLIC_POLICY` 또는 `SOCIETY` + 정치 검토

## 3.4 Secondary Category 사용 제한

Secondary Category는 교차 주제를 표현하되 Primary Category를 우회하는 용도로 쓰지 않는다.

- 최대 2개
- 추천 다양성 계산에서는 Primary를 우선
- Risk 분류에는 모든 관련 축을 반영
- 정치 관련성이 있으면 Secondary에만 넣고 일반 처리하지 않음

## 3.5 분류 신뢰도

자동 분류 결과에는 `classification_confidence`를 둔다.

```text
HIGH_CONFIDENCE
MEDIUM_CONFIDENCE
LOW_CONFIDENCE
HUMAN_REQUIRED
```

다음은 인간 검토로 보낸다.

- 정치 여부가 불명확함
- 두 개 이상의 Primary 후보가 비슷함
- 특정 인물·집단이 포함됨
- 건강·법률·금융·미성년자 민감 주제
- 모델과 룰 엔진이 다른 Risk를 제안함

# 4. 대분류 코드와 전체 구조

## 4.1 대분류 목록

| 코드 | 사용자 표시명 | 핵심 범위 | 기본 Risk | 유희형 적합성 | 기본 출처 요건 |
|---|---|---|---|---|---|
| `LIFE` | 생활 | 음식, 주거, 이동, 취미, 반려동물, 생활매너 | LOW | 매우 높음 | Evergreen은 없음 가능 |
| `RELATIONSHIP` | 인간관계 | 연애, 친구, 가족, 결혼, 경계, 세대 관계 | LOW~MEDIUM | 높음 | 경험형은 없음 가능 |
| `WORK_CAREER` | 직장·커리어 | 직장문화, 회식, 업무시간, 취업, 이직, 재택 | MEDIUM | 높음 | 정책·통계는 필요 |

## 4.2 카테고리 운영 원칙

- 대분류는 출시 전 안정화하고 자주 추가하지 않는다.
- 하위 분류와 Topic은 운영 데이터에 따라 확장한다.
- 사용자 온보딩에는 내부 분류 전체를 그대로 노출하지 않는다.
- 카테고리와 위험도는 독립적으로 저장한다.
- 같은 질문을 여러 대분류에 중복 게시하지 않는다.
- 지역·언어 차이는 카테고리 코드가 아니라 별도 축으로 관리한다.

# 5. Topic, Tag, Entity 체계

## 5.1 Topic의 역할

Topic은 대분류보다 세밀한 관심사를 표현한다.

예:

```text
Primary Category: TECH
Subcategory: AI
Topics: GENERATIVE_AI, WORK_AUTOMATION, CREATIVE_TOOLS
```

Topic은 다음에 사용한다.

- 관심사 온보딩의 2단계 확장
- 후보 Retrieval
- 사용자 행동 기반 affinity
- 유사 Issue 클러스터
- 카테고리 내부 다양성
- 특정 Topic 과다 노출 제어

## 5.2 Controlled Topic과 Free Tag 분리

### Controlled Topic

운영자가 코드와 정의를 관리한다.

- 분석과 ML Feature에 사용
- 동의어를 하나의 코드로 통합
- 버전과 Deprecated 상태 관리

### Free Tag

편집·검색 보조용이다.

- 새로운 유행어·작품명·행사명
- 운영자가 검토 후 Controlled Topic 승격 가능
- 추천 핵심 Feature로 바로 사용하지 않음

## 5.3 Entity

Entity는 실제 인물·기관·제품·작품·사건을 나타낸다.

```text
PERSON
ORGANIZATION
PRODUCT
WORK
EVENT
LOCATION
POLITICAL_ENTITY
```

Entity가 포함되면 다음을 추가 검사한다.

- 실존 여부와 이름 정확성
- 공인인지 사인인지
- 최신 맥락과 날짜
- 명예훼손·사생활·정치 분류
- 중복 Issue

## 5.4 Topic 수 제한

- 최소 1개
- 기본 최대 5개
- 모델이 과도하게 많은 Topic을 붙이면 인간 검수
- 단순 단어 중복을 Topic으로 만들지 않음

## 5.5 사용자에게 보이는 Topic

내부 Topic을 그대로 모두 노출하지 않는다.

예:

```text
Internal: WORKPLACE_ASYNC_COMMUNICATION
User label: 퇴근 후 연락
```

표시 라벨은 이해하기 쉽고 중립적이어야 한다.

# 6. Experience Mode — 사용자가 느끼는 콘텐츠 경험

## 6.1 Experience Mode의 목적

같은 카테고리라도 사용자가 느끼는 경험은 다르다.

```text
AI 도구는 다크모드가 더 좋다?
→ PLAYFUL_QUICK

회사가 AI 사용 내역을 직원 평가에 활용해도 될까?
→ PRACTICAL_JUDGMENT

정부가 선거 광고의 생성형 AI 사용을 규제해야 할까?
→ RESTRICTED_POLITICAL
```

**[확정]** 모든 Published Issue는 하나의 `experience_mode`를 가진다.

## 6.2 Experience Mode 목록

| 코드 | 의미 | 목표 반응 | 맥락 비용 | 기본 Risk |
|---|---|---|---:|---|
| `PLAYFUL_QUICK` | 취향·가벼운 선택·즉답 | 빠른 투표, 연속 소비 | 매우 낮음 | LOW |
| `RELATABLE_DILEMMA` | 일상에서 겪는 관계·규칙 딜레마 | 공감, 댓글 | 낮음 | LOW~MEDIUM |
| `HYPOTHETICAL_CHOICE` | 무해한 가상 조건·트레이드오프 | 재미, 공유 | 낮음 | LOW |
| `CULTURE_PULSE` | 작품·게임·콘텐츠·트렌드 취향 | 현재성, 팬 참여 | 낮음~중간 | LOW~MEDIUM |
| `PRACTICAL_JUDGMENT` | 직장·소비·기술의 실용 판단 | 자기 경험 비교 | 중간 | MEDIUM |
| `PUBLIC_DELIBERATION` | 사회 제도·공공 선택 | 숙고, 양측 이유 | 중간~높음 | MEDIUM~HIGH |
| `RESTRICTED_POLITICAL` | 정치·선거·정당·현 정부 | 제한된 참여 | 높음 | RESTRICTED |

## 6.3 모드별 작성 계약

### `PLAYFUL_QUICK`

- 한 번 읽고 3초 안에 선택 의미를 이해할 수 있어야 한다.
- 배경 없이도 답할 수 있는 질문을 우선한다.
- 결과를 친구와 비교하고 싶은 요소가 있으면 좋다.
- 특정 집단·개인을 희화화하지 않는다.

### `RELATABLE_DILEMMA`

- 사용자가 경험을 떠올릴 수 있는 구체적 상황을 사용한다.
- 한쪽을 비도덕적 사람으로 만들지 않는다.
- 조건을 과도하게 생략해 오해를 만들지 않는다.

### `HYPOTHETICAL_CHOICE`

- 조건이 명확하고 무해해야 한다.
- 현실의 피해자·비극·질병을 가상 놀이로 사용하지 않는다.
- 선택 불가능한 억지 조건은 피한다.

### `CULTURE_PULSE`

- 작품명·서비스명·발표 시점을 정확히 표시한다.
- 스포일러가 있으면 고지한다.
- 팬덤 공격과 실존 인물 사생활로 이동하지 않는다.

### `PRACTICAL_JUDGMENT`

- 사용자가 판단할 기준을 이해할 수 있도록 조건을 명확히 한다.
- 법률·금융·건강 조언으로 오인되지 않게 한다.

### `PUBLIC_DELIBERATION`

- 배경과 출처를 제공한다.
- 정책 효과를 사실로 단정하지 않는다.
- 가치 판단과 사실 설명을 분리한다.

### `RESTRICTED_POLITICAL`

- 강화된 출처·중립성·인간 검수 계약을 적용한다.
- 일반 Engagement 목표보다 무결성과 비대표성 고지를 우선한다.

# 7. 유희 우선 시딩과 초기 경험 믹스

## 7.1 유희성의 제품적 정의

WHICH에서 유희성은 단순히 웃긴 문장을 의미하지 않는다.

> 사용자가 배경 지식이나 큰 심리 부담 없이 자신의 취향·경험·상상을 즉시 선택하고, 다른 사람과 결과를 비교하는 재미를 느끼는 정도다.

유희성은 다음 특성의 조합이다.

- 낮은 인지 비용
- 즉시 답할 수 있음
- 개인 경험과 연결됨
- 선택 결과가 궁금함
- 공유·비교하고 싶음
- 공격성 없이 의외성이 있음
- 같은 포맷으로 시리즈화 가능함

## 7.2 초기 Active Pool 경험 믹스

**[초기안]** 출시 초기 전체 Eligible Pool은 다음 경험 비중을 목표로 한다.

```text
PLAYFUL_QUICK + HYPOTHETICAL_CHOICE  40~50%
RELATABLE_DILEMMA                    20~25%
CULTURE_PULSE                        10~15%
PRACTICAL_JUDGMENT                   10~20%
PUBLIC_DELIBERATION                   5~10%
RESTRICTED_POLITICAL                  0~3%
```

`RESTRICTED_POLITICAL`은 콘텐츠 준비가 되어도 일반 신규 사용자 첫 세션에는 포함하지 않는다.

## 7.3 신규 Guest 첫 10개 슬롯

**[초기안]** 관심사 정보가 없는 Guest에게는 다음과 같이 구성한다.

| 슬롯 범위 | 목표 |
|---|---|
| 1~2 | 가장 이해하기 쉬운 `PLAYFUL_QUICK` |
| 3~4 | 서로 다른 카테고리의 `RELATABLE_DILEMMA` |
| 5 | 전체 인기 중 LOW~MEDIUM |
| 6~7 | 문화·게임·테크 등 발견형 |
| 8 | 가벼운 Exploration |
| 9 | 접전 가능성이 높은 저위험 Issue |
| 10 | 사용자의 앞선 행동을 반영한 첫 개인화 |

가드레일:

- 첫 5개 중 동일 대분류 최대 2개
- 첫 10개에 최소 4개 대분류
- HIGH·RESTRICTED 제외
- 실존 개인 평가 연속 노출 금지
- 같은 질문 클러스터 연속 노출 금지
- 정확한 접전 비율은 투표 전 숨김

## 7.4 관심사 선택 후 첫 세션

관심사 3개를 선택한 회원에게도 유희 비중을 유지한다.

```text
60% 선택 관심사 안의 유희·공감형
20% 전체 인기·문화 Pulse
10% 인접 관심사
10% Exploration
```

초기 선택이 `경제`, `사회`, `교육`처럼 무거운 주제여도 첫 세션 전체가 공공 이슈로만 채워지지 않게 한다.

## 7.5 유희형 시리즈 예시

내부 편집 시리즈 후보:

- `오늘의 밸런스` — 두 취향 중 하나
- `생활 심판` — 일상 행동이 괜찮은지
- `하나만 남긴다면` — 무해한 가상 선택
- `직장인의 선택` — 가벼운 직장 딜레마
- `콘텐츠 취향전` — 영화·게임·음악 방식 비교
- `기술 취향전` — 기기·앱·AI 사용 방식
- `여행 한 가지` — 숙소·음식·일정 등 우선순위

이 명칭은 내부안이며 최종 브랜드 카피는 별도 UX 검토가 필요하다.

## 7.6 유희성 가드레일

**[금지]** 다음은 Playfulness로 점수를 올리지 않는다.

- 외모·몸무게·질병·장애를 선택 대상으로 삼음
- 인종·국적·성별·성적 지향·종교를 희화화함
- 범죄·재난·사망·피해자를 가상 게임으로 소비함
- 특정 개인의 사생활·연애·루머를 밸런스 게임화함
- 미성년자 관련 성적·모욕적 질문
- 한쪽 선택을 패배자·비정상으로 조롱함
- 허위 수치나 조작된 이미지를 사용함
- 자극적인 표현만 있고 실제 선택 의미가 없음

# 8. Playfulness Score

## 8.1 목적

Playfulness Score는 Quality Score를 대체하지 않는다.

```text
Quality Eligibility 통과
→ Experience Mode가 유희형이면 Playfulness Score 평가
→ 초기 공급·첫 세션 우선순위에 사용
```

공공정책·정치 질문은 Playfulness가 낮아도 품질이 낮은 것이 아니다.

## 8.2 점수 구성

**[초기안]** 0~100점으로 계산한다.

| 항목 | 배점 | 판정 질문 |
|---|---:|---|
| 즉시 이해 가능성 | 20 | 한 번 읽고 A/B 의미를 바로 이해하는가? |
| 개인적 관련성 | 20 | 자신의 취향·경험을 떠올리기 쉬운가? |
| 결과 호기심 | 20 | 다른 사람의 선택 분포가 궁금한가? |
| 무해한 의외성 | 15 | 예상 밖의 대비나 재미가 있는가? |
| 공유·비교 가능성 | 15 | 친구와 결과를 비교하고 싶은가? |
| 시리즈 확장성 | 10 | 동일 포맷으로 반복 공급 가능한가? |
| **합계** | **100** |  |

## 8.3 점수 구간

| 점수 | 의미 | 처리 |
|---:|---|---|
| 85~100 | 강한 유희형 | 첫 세션·시딩 우선 후보 |
| 70~84 | 충분한 유희형 | 일반 Playful Pool |
| 55~69 | 보통 | 다른 품질·관심사 신호와 결합 |
| 0~54 | 유희형으로 약함 | 다른 Experience Mode 재분류 검토 |

## 8.4 자동 추정과 인간 검수

AI는 Playfulness Score를 제안할 수 있지만 다음 항목은 인간이 확인한다.

- 웃음이나 의외성이 타인 비하에서 발생하는가?
- 문화권·연령에 따라 모욕적으로 해석될 수 있는가?
- 질문이 지나치게 사적인 정보를 요구하는가?
- 실제로는 정답이 명백한데 선택 놀이처럼 포장했는가?

## 8.5 제품 KPI와의 검증

Playfulness Score가 높은 질문이 실제로 다음 지표를 높이는지 검증한다.

- First Vote Conversion
- Median Time to First Vote
- Votes per Session
- Next Issue Rate
- Share Rate
- Skip Rate
- Report Rate

Playfulness Score가 높아도 신고율이나 즉시 이탈이 높으면 평가식을 재조정한다.

# 9. 관심사 온보딩과 Taxonomy 연결

## 9.1 사용자에게 보여줄 대분류

내부 10개 대분류를 그대로 보여주기보다 이해하기 쉬운 관심사 카드로 구성한다.

**[초기안]**

```text
음식·생활
연애·관계
직장·커리어
영화·드라마
음악
게임
IT·AI
스포츠
여행·취미
경제·소비
교육
사회
```

정치·선거는 신규 관심사 온보딩의 기본 추천 카드에서 제외하거나 별도 설정으로 분리한다.

## 9.2 관심사 카드와 내부 코드 매핑

| 사용자 카드 | 내부 매핑 예 |
|---|---|
| 음식·생활 | `LIFE/FOOD`, `LIFE/HOME`, `LIFE/ETIQUETTE` |
| 연애·관계 | `RELATIONSHIP/*` |
| 영화·드라마 | `CULTURE_ENT/FILM_TV` |
| 게임 | `CULTURE_ENT/GAME`, `SPORTS/ESPORTS` 일부 |
| IT·AI | `TECH/AI`, `TECH/DEVICE`, `TECH/PLATFORM` |
| 경제·소비 | `ECONOMY_CONSUMPTION/*` |
| 사회 | `SOCIETY/*` |

## 9.3 정치 관심사 처리

- 정치 관심 여부와 정치적 입장 방향을 분리한다.
- A/B 선택을 정당·이념 성향 Feature로 전환하지 않는다.
- 일반 관심사 카드에서 정치 선택을 강요하지 않는다.
- 정치 Feed는 별도 권한·고지·무결성 정책을 적용한다.

## 9.4 관심사 변경

사용자는 설정에서 관심 Topic을 추가·삭제할 수 있다.

- 명시적 선택은 높은 초기 가중치
- 실제 투표·Skip 행동으로 점진 갱신
- `이 주제 덜 보기`는 Negative Signal
- 초기 선택이 영구적 필터가 되지 않도록 Exploration 유지

# 10. Lifecycle Type과 Experience Mode의 관계

## 10.1 Lifecycle Type

| 코드 | 의미 |
|---|---|
| `EVERGREEN` | 특정 날짜에 크게 의존하지 않음 |
| `CURRENT` | 현재 뉴스·정책·제품·사건 맥락이 중요함 |
| `TREND` | 짧은 기간 급상승한 화제 |
| `EDITORIAL` | WHICH가 기획한 테마·시리즈 |
| `USER_GENERATED` | 회원 제안 기반 |
| `FOLLOW_UP` | 기존 Issue 결과나 사건 변화의 후속 |
| `SEASONAL` | 반복되는 시기·행사 기반 |

## 10.2 두 축은 독립적이다

예:

| Lifecycle | Experience | 예시 |
|---|---|---|
| EVERGREEN | PLAYFUL_QUICK | 탕수육은 부먹인가 찍먹인가? |
| CURRENT | CULTURE_PULSE | 새로 공개된 게임의 시즌제는 필요한가? |
| EDITORIAL | RELATABLE_DILEMMA | 퇴근 후 업무 메신저에 답해야 할까? |
| CURRENT | PUBLIC_DELIBERATION | 대중교통 요금 정책을 바꿔야 할까? |
| CURRENT | RESTRICTED_POLITICAL | 특정 선거 공약을 추진해야 할까? |

수명과 경험을 하나의 코드로 합치지 않는다.

# 11. Risk Level

## 11.1 Risk 정의

Risk Level은 다음 가능성을 종합한다.

- 개인·집단 피해
- 사실 오류의 영향
- 법률·규제 위험
- 조직적 조작 가능성
- 2차 피해와 사생활 침해
- 추천 증폭 시 사회적 비용
- 운영자의 전문 검토 필요성

## 11.2 Level 정의

### `LOW`

- 일상 취향, 음식, 취미, 무해한 가상 선택
- 피해 가능성이 낮고 외부 사실 의존이 적음
- 자동 검사 후 인간 최종 승인 또는 성숙 후 제한적 자동 승인 후보

### `MEDIUM`

- 직장, 교육, 경제, 사회 규칙, 특정 이해관계
- 사실 배경이나 조건이 결과 해석에 영향을 줌
- AI 품질·안전 검사와 인간 검수 또는 표본 검수

### `HIGH`

- 보호 집단, 젠더, 종교, 범죄·사건, 특정 개인
- 건강·안전·법률·금융, 미성년자
- 2차 피해·명예훼손·잘못된 행동 유도 가능성
- 인간 승인과 노출 제한, 강화된 모니터링

### `RESTRICTED`

- 정치인, 정당, 선거, 후보, 캠페인, 현 정부 정책 평가
- 조직적 여론 개입 가능성이 높음
- 별도 파이프라인, 인간 승인, 강화된 신원·투표·추천 정책

## 11.3 Fail-Closed 원칙

자동 분류가 Risk를 확신하지 못하면 낮은 Level을 선택하지 않는다.

```text
LOW vs MEDIUM 불확실
→ MEDIUM 후보

MEDIUM vs HIGH 불확실
→ HIGH 후보

정치 관련성 불확실
→ RESTRICTED 검토 큐
```

# 12. Sensitivity Flag와 Risk 상승 요인

## 12.1 주요 Sensitivity Flag

| 코드 | 의미 | 기본 조치 |
|---|---|---|
| `POLITICAL_ENTITY` | 정치인·정당·후보·선거기관 | RESTRICTED 검토 |
| `ELECTION_RELATED` | 선거·투표·캠페인 | RESTRICTED |
| `PROTECTED_CLASS` | 인종·국적·성별·장애·종교 등 | HIGH 이상 |
| `PRIVATE_PERSON` | 비공인 실존 개인 | 원칙적 제한·제거 검토 |
| `PUBLIC_FIGURE` | 공인·연예인·선수 | 사실·사생활 검수 |
| `MINOR` | 미성년자 | HIGH 이상 |
| `CRIME_TRAGEDY` | 범죄·재난·사망·피해 | HIGH |
| `HEALTH_MEDICAL` | 건강·의료 | HIGH 또는 전문 검토 |
| `LEGAL` | 법률·계약·권리 | HIGH 또는 전문 검토 |
| `FINANCIAL` | 투자·재무·수익 | HIGH 또는 제한 |
| `SEXUAL_CONTENT` | 성적 내용 | HIGH 또는 금지 |
| `SELF_HARM` | 자해·자살 | 전문 안전 정책 적용 |
| `PERSONAL_DATA` | 개인정보·위치·신상 | 차단 또는 HIGH |
| `ACTIVE_DISPUTE` | 현재 진행 중 분쟁 | 강화 검토 |
| `UNVERIFIED_CLAIM` | 핵심 주장이 미확인 | 게시 보류 |
| `RIGHTS_UNCLEAR` | 이미지·본문 권리 불명 | 게시 보류 |

## 12.2 Risk 상승 규칙

다음은 카테고리 기본 Risk보다 높은 Level을 적용한다.

```text
보호 집단 + 부정적 일반화
→ HIGH 또는 REJECT

실존 개인 + 확인되지 않은 비난
→ HIGH / REJECT

미성년자 + 사생활·성적 내용
→ BLOCK

범죄 피해 + 유희형 포맷
→ BLOCK

정치 Entity + 현재 정책·지지 판단
→ RESTRICTED

투자 자산 + 매수·매도 유도
→ HIGH / 제한
```

## 12.3 복수 Flag

Sensitivity Flag가 여러 개면 가장 높은 Risk를 기본으로 하며 조합 위험을 별도 고려한다.

예:

```text
PUBLIC_FIGURE + POLITICAL_ENTITY + ELECTION_RELATED
→ RESTRICTED

MINOR + CRIME_TRAGEDY
→ HIGH + 특별 보호
```

# 13. 정치·공공정책 경계 기준

## 13.1 직접 RESTRICTED

다음은 즉시 `RESTRICTED`로 보낸다.

- 특정 후보·정당에 대한 지지 또는 반대
- 선거 공약·캠페인·투표 행동
- 현직 정치인의 직무·정책 평가
- 정당·정부의 성과 비교
- 선거제도·개표·투표 절차에 대한 정치적 판단
- 외교·안보 이슈가 정부·정당 지지와 직접 연결됨

## 13.2 사회·경제 정책과의 경계

다음은 `SOCIETY` 또는 `ECONOMY_CONSUMPTION`으로 남을 수 있지만 정치 검토가 필요하다.

```text
일회용 컵 보증금 제도는 필요한가?
```

- 특정 정당·정부·후보 언급 없음
- 일반 제도 설계에 초점
- MEDIUM~HIGH 가능

```text
현 정부의 일회용 컵 보증금 정책을 지지하는가?
```

- 현 정부 평가와 연결
- RESTRICTED

## 13.3 정치성 우회 금지

**[금지]** 정치 질문을 일반 카테고리로 보이게 하려고 인물명만 제거하거나 Secondary Category에 숨기지 않는다.

## 13.4 정치 결과와 추천

- 일반 `For You`의 Engagement Boost를 그대로 적용하지 않는다.
- 정확한 참여 결과는 대표 여론으로 표현하지 않는다.
- 외부 유입 급증 시 추천을 자동 증폭하지 않는다.
- 정치 선택 방향으로 개인 정치 성향을 생성하지 않는다.

# 15. Question Archetype

## 15.1 유형 목록

| 코드 | 구조 | 예시 |
|---|---|---|

다음은 별도 설계 전까지 기본 제외 또는 신중 검토한다.

- `PREDICTION`: 미래 사실 예측
- `KNOWLEDGE_QUIZ`: 정답이 있는 사실 문제
- `RATING_SCALE`: 1~5점 평가
- `MULTI_OPTION`: 3개 이상 선택
- `RANKING`: 여러 대상을 순위화
- `BETTING`: 금전·보상 예측

WHICH의 핵심은 A/B 의견 선택이며, 다른 형식은 제품 정체성이 확인된 뒤 확장한다.

# 16. Binary Fit 판정

## 16.1 필수 검사

게시 가능한 A/B Issue는 다음 질문에 모두 `예`로 답해야 한다.

1. 질문에 하나의 주 판단 축이 있는가?
2. A와 B가 질문에 직접 답하는가?
3. 두 선택지의 의미가 구분되는가?
4. 두 선택지가 동시에 참이 되는 구조가 아닌가?
5. 대부분의 사용자가 둘 중 하나를 의미 있게 선택할 수 있는가?
6. `조건부`, `둘 다`, `상황에 따라`가 사실상 필수 제3선택이 아닌가?
7. 정답이 있는 사실 퀴즈가 아닌가?
8. 한쪽 선택이 불법·폭력·차별을 정상화하지 않는가?
9. 질문이 허위 전제를 포함하지 않는가?
10. 결과가 무엇을 의미하는지 한 문장으로 설명할 수 있는가?

## 16.2 Binary Fit 실패 유형

| 코드 | 의미 | 예시 처리 |
|---|---|---|
| `MULTI_AXIS` | 여러 논점 혼합 | 질문 분리 |
| `MISSING_THIRD_OPTION` | 필수 제3선택 존재 | 질문 좁힘 또는 폐기 |
| `OVERLAP` | A와 B가 겹침 | 선택지 재작성 |
| `NON_EXHAUSTIVE` | 핵심 경우를 포함하지 못함 | 범위 명시 |
| `FACT_QUIZ` | 정답이 있는 문제 | 게시 형식 부적합 |
| `HARMFUL_OPTION` | 유해 입장 정상화 | 거절 |
| `FALSE_PREMISE` | 허위·미검증 전제 | 출처 보강 또는 거절 |
| `VAGUE_TARGET` | 무엇을 평가하는지 모호 | 대상 구체화 |

## 16.3 질문 좁히기 예

```text
나쁜 질문
AI 사용은 좋은가?
```

범위가 너무 넓다.

```text
개선
회사 내부 문서 초안 작성에 생성형 AI 사용을 허용해야 할까?
A. 허용해야 한다
B. 제한해야 한다
```

## 16.4 조건부 의견 처리

질문 자체에 공통 조건을 넣어 이지선다 적합성을 높인다.

```text
모호함
카페에서 오래 공부하는 것은 민폐인가?

개선
혼잡 시간대에 카페 좌석을 3시간 이상 사용하는 것은 민폐인가?
A. 민폐다
B. 괜찮다
```

조건을 추가해도 핵심 제3선택이 남으면 게시하지 않는다.

# 17. Universal Issue Quality Rule

## 17.1 Hard Gate

다음 중 하나라도 해당하면 점수와 무관하게 게시하지 않는다.

- 질문이 이해되지 않음
- Binary Fit 실패
- A/B 의미가 겹치거나 비대칭
- 특정 답을 노골적으로 유도함
- 사실 퀴즈 또는 명백한 정답만 존재함
- 허위·미검증 전제를 사실처럼 사용함
- 특정 개인·집단 공격 또는 신상 노출
- 유해 행위를 정상화함
- 출처가 필요한데 증거가 없음
- 정치 Issue가 일반 큐로 들어옴
- 기존 Published Issue와 실질적 중복
- 권리 불명확 미디어가 필수 요소임
- 질문의 의미를 안정적으로 번역·표시할 수 없음

## 17.2 Universal Rule

1. 한 질문에는 한 판단 축만 둔다.
2. 질문의 대상, 범위, 시점을 이해할 수 있어야 한다.
3. A와 B 모두 현실적으로 선택 가능한 입장이어야 한다.
4. 두 선택지는 표현 강도와 구체성이 대등해야 한다.
5. 질문과 선택지에 감정적 유도 표현을 넣지 않는다.
6. 맥락이 필요하면 짧고 검증된 배경을 제공한다.
7. 특정 개인·집단의 존엄이나 안전을 해치지 않는다.
8. 사용자의 선택을 대표 여론이나 사실 판정으로 과장하지 않는다.
9. 문장은 모바일에서 빠르게 읽을 수 있어야 한다.
10. 결과를 봤을 때 사용자가 무엇을 선택했는지 명확해야 한다.
11. 기존 이슈와 의미 중복을 피한다.
12. 게시 후 질문 의미를 유지할 수 있어야 한다.

# 19. 질문 문장 작성 규칙

## 19.1 질문 길이

- 모바일 두세 줄 안에서 핵심 의미가 드러나도록 한다.
- 불필요한 배경은 질문에서 분리한다.
- 짧게 만들기 위해 조건을 삭제해 의미를 왜곡하지 않는다.

## 19.2 문장 구조

권장:

```text
[대상] + [행동·정책·선호] + [판단 질문]
```

예:

```text
퇴근 후 업무 메신저에 응답하는 것도 업무의 일부라고 볼 수 있을까?
```

## 19.3 날짜와 시점

Current·Trend·정책 질문은 상대 날짜보다 절대 날짜나 기준 시점을 사용한다.

```text
나쁜 예: 최근 발표된 정책
좋은 예: 2026년 8월 발표된 ○○ 정책
```

## 19.4 유도 표현 금지

다음 표현은 특별한 이유 없이 사용하지 않는다.

- 당연히
- 아직도
- 무능한
- 비상식적인
- 개념 없는
- 정상이라면
- 반드시
- 착한 사람이라면
- 피해를 막기 위해서라도

## 19.5 이중 부정 제한

```text
나쁜 예
```

부정 구조는 한 번만 사용하고 A/B 의미를 직접적으로 쓴다.

## 19.6 질문과 공유 카피 분리

Published Issue는 중립적으로 유지한다. SNS 공유 카피도 질문 의미를 왜곡하거나 분노를 유도하지 않는다.

# 20. A/B 선택지 대칭성

## 20.1 대칭성 검사 축

두 선택지를 다음 항목으로 비교한다.

- 문장 길이
- 구체성
- 감정 강도
- 도덕적 가치
- 행위 범위
- 시간 범위
- 책임 수준
- 조건절 수
- 긍정·부정 프레이밍

## 20.2 좋은 구조

```text
A. 허용해야 한다
B. 제한해야 한다
```

```text
A. 숙소가 더 중요하다
B. 음식이 더 중요하다
```

## 20.3 나쁜 구조

```text
A. 노동자의 정당한 권리를 위해 반드시 허용해야 한다
B. 허용하면 안 된다
```

A에만 도덕적 이유와 강한 수식어가 있다.

## 20.4 A/B 위치 편향

- A를 긍정, B를 부정으로 항상 고정하지 않는다.
- 선택지 위치 자체를 랜덤화할지는 투표 무결성과 UX 실험에서 별도 결정한다.
- 위치를 랜덤화하면 결과·댓글의 `A/B` 라벨 의미가 흔들릴 수 있으므로 신중히 검토한다.
- 첫 정상 투표 이후 A/B 위치를 변경하지 않는다.

## 20.5 YES/NO의 비대칭

질문이 복잡하면 단순 `예/아니오`보다 의미를 다시 써준다.

```text
질문: 수업 중 생성형 AI 사용을 허용해야 할까?
A. 허용해야 한다
B. 제한해야 한다
```

이 방식이 단순 `예/아니오`보다 결과 해석에 유리하다.

# 23. 중복·유사 Issue

## 23.1 중복 정의

다음은 하나의 의미 클러스터로 본다.


## 23.2 중복 유형

| 유형 | 설명 | 처리 |
|---|---|---|
| Exact | 문장이 동일 | 게시 차단 |
| Paraphrase | 표현만 다름 | 기존 Issue 연결 |
| Semantic | 핵심 판단이 동일 | 병합·차단 검토 |
| Event Duplicate | 같은 사건·자료 | 하나의 대표 Issue |
| Scope Variant | 지역·시점·조건이 다름 | 차이가 실질적이면 허용 |
| Follow-up | 사건 변화로 판단 대상이 달라짐 | Successor 관계 |

## 23.3 유희형 중복 관리

유희형은 포맷 반복이 많기 때문에 다음을 별도로 본다.

- 같은 질문의 단어만 교체한 대량 생성
- 항상 같은 카테고리의 `A vs B`
- 결과가 사실상 예측 가능한 상식형 반복
- 동일 세션에서 유사 구조 연속 노출

## 23.4 Cluster Feature

각 Issue는 가능하면 `semantic_cluster_id`를 가진다.

추천에서는:

- 동일 클러스터 연속 노출 금지
- 사용자에게 이미 본 의미의 질문 제외
- 실험군 간 중복 오염 방지

# 24. 논쟁 피드의 정의

## 24.1 핵심 정의

**[확정]** `논쟁`은 정상 집계된 A/B 투표 결과가 50:50에 가까운 접전 Issue의 피드다.

```text
A 50.8%
B 49.2%
```

이런 분포가 대표적이다.

## 24.2 논쟁이 아닌 것

다음은 반응이 크더라도 `논쟁` 정의와 다르다.

- 댓글 욕설이 많은 Issue
- 신고가 많은 Issue
- 정치 커뮤니티가 충돌한 Issue
- 한쪽이 90%지만 댓글이 과열된 Issue
- 조회수만 많은 Issue

필요하면 별도 내부 신호로 관리하되 `논쟁` 라벨로 사용자에게 노출하지 않는다.

## 24.3 결과 비공개 원칙과의 조화

사용자가 아직 투표하지 않았다면:

```text
🔥 현재 접전 중
```

처럼 방향을 밝히지 않는 라벨만 제공한다.

투표 후에는:

```text
A 50.8%
B 49.2%
정상 참여 12,821명
```

을 공개한다.

# 25. Controversy Score

## 25.1 Balance Score

A의 정상 투표 비율을 `p`라고 할 때:

```text
Balance Score = 1 - 2 × |p - 0.5|
```

범위는 0~1이다.

| A:B | Balance Score |
|---|---:|
| 50:50 | 1.00 |
| 52:48 | 0.96 |
| 55:45 | 0.90 |
| 60:40 | 0.80 |
| 70:30 | 0.60 |
| 90:10 | 0.20 |
| 100:0 | 0.00 |

## 25.2 최종 점수 개념식

```text
Controversy Score
=
Balance Score
× Sample Confidence
× Integrity Factor
× Stability Factor
× Freshness Factor
```

선택적으로 충분한 댓글이 있을 때만 `Comment Balance Modifier`를 소폭 적용할 수 있다.

## 25.3 각 Factor의 의미

### Sample Confidence

저표본 50:50을 상위로 올리지 않기 위한 신뢰 계수다.

### Integrity Factor

정상 투표 비율, Review·Invalid 비중, 비정상 유입 상태를 반영한다.

### Stability Factor

최근 몇 표에 따라 결과가 크게 흔들리는 초기 상태를 낮춘다.

### Freshness Factor

`현재 접전` 피드의 시의성을 반영한다. 장기 통계용 Balance와는 분리한다.

# 26. 표본 신뢰와 초기 임계값

## 26.1 단계별 등급

**[초기안]** 트래픽이 충분히 쌓이기 전 다음 등급을 사용한다.

| 등급 | 정상 투표 수 | 비율 조건 | 용도 |
|---|---:|---|---|
| `EMERGING_CLOSE` | 50 이상 | 45:55 이내 | 내부 후보·실험 |
| `QUALIFIED_CLOSE` | 200 이상 | 45:55 이내 | 일반 논쟁 피드 후보 |
| `VERY_CLOSE` | 500 이상 | 48:52 이내 | `초접전` 라벨 후보 |
| `FEATURED_CLOSE` | 1,000 이상 또는 카테고리 상위 표본 | 47:53 이내 | 홈 대표 카드 후보 |

정확한 수치는 트래픽 규모와 카테고리별 참여량을 보고 조정한다.

## 26.2 동적 임계값

서비스가 성장하면 절대 표본만으로 판단하지 않는다.

```text
Minimum Sample
=
max(
  절대 최소값,
  해당 카테고리·시간창 정상 투표의 일정 분위수
)
```

저활성 카테고리를 영구적으로 배제하지 않도록 별도 카테고리 슬롯을 둘 수 있다.

## 26.3 Bayesian Smoothing

초기 몇 표의 극단적 변동을 줄이기 위해 Beta Prior 또는 동등한 Smoothing을 적용할 수 있다.

**[설계 기준]** 사용자에게 표시하는 실제 정상 투표 수와 운영 랭킹에 사용하는 안정화 추정치는 구분한다.

## 26.4 저표본 표시

논쟁 Feed 자격을 얻지 못했더라도 결과 화면에는 다음처럼 표시할 수 있다.

```text
참여 초기입니다.
결과는 참여가 늘면서 크게 달라질 수 있습니다.
```

# 27. Integrity와 논쟁 피드

## 27.1 Eligibility Gate

다음 상태는 논쟁 피드에서 제외한다.

- `UNDER_REVIEW`
- `RESULT_LOCKED`
- `LIMITED` 중 무결성 제한
- 비정상 유입 경보가 높은 상태
- 정상 투표보다 Review·Invalid 비중이 높은 상태
- 정치 Issue의 일반 논쟁 피드 노출

## 27.2 Integrity Factor 초기안

개념적으로 다음 신호를 반영한다.

- Accepted Vote 비율
- 중복·자동화 의심 비율
- Referrer 집중도
- 신규 세션 폭증
- Challenge 실패율
- 계정 생성 직후 집중 참여

정확한 공격 탐지 규칙은 `05_IDENTITY_AND_VOTE_INTEGRITY`에서 정의한다.

## 27.3 실제 바이럴과 공격 구분

외부 유입이 크다는 이유만으로 자동 제외하지 않는다.

```text
유입 급증
→ 노출 자동 증폭 중단
→ Integrity 평가
→ 정상 바이럴이면 유지
→ 조직적 조작이면 제한·검토
```

# 28. 댓글 신호와 논쟁

## 28.1 댓글은 보조 신호다

댓글 균형은 충분한 표본이 있을 때만 사용한다.

```text
Vote Balance
= 핵심

Comment Balance
= 보조
```

## 28.2 Comment Balance 조건

- 양쪽 합계 최소 댓글 수 충족
- 삭제·스팸·복제 댓글 제외
- 한 사용자의 반복 댓글로 균형 왜곡 방지
- 좋아요 수만으로 의견 크기를 추정하지 않음

## 28.3 의견 다양성

전체 댓글 탭에서는 다수 의견만 상단을 독점하지 않도록 Re-ranking할 수 있다.

그러나 댓글 노출 균형을 투표 결과 자체와 혼동하지 않는다.

```text
댓글을 50:50으로 보여줌
≠
투표가 50:50임
```

# 29. 논쟁 피드 UX 계약

## 29.1 투표 전 카드

표시 가능:

- 질문
- A/B 선택지
- 카테고리
- `접전 중` 또는 `초접전` 라벨
- 정상 참여 수의 범주형 표현 또는 정확 수치

기본 비표시:

- A와 B의 정확한 퍼센트
- 어느 쪽이 우세한지
- 사용자가 어느 쪽을 선택해야 접전이 유지되는지 암시하는 문구

## 29.2 투표 후 결과

- 정확한 A/B 비율
- 정상 참여 수
- 사용자의 선택
- `당신과 같은 선택` 비율
- 저표본·검토·비대표성 고지

## 29.3 정치 Issue

정치·선거 Issue는 일반 논쟁 탭과 분리하거나 노출 상한을 둔다.

- `논쟁 1위`가 정치적 대표성으로 오인되지 않게 함
- 조직적 유입이 급증하면 결과 잠금 가능
- 비대표성 고지를 항상 표시

## 29.4 라벨 기준

**[초기안]**

| 라벨 | 조건 예 |
|---|---|
| 접전 중 | Qualified + 45:55 이내 |
| 초접전 | Qualified + 48:52 이내 |
| 결과 변동 가능 | 표본 또는 안정성 부족 |
| 검토 중 | Integrity·출처 검토 |

# 30. 카테고리·경험·Risk 다양성

## 30.1 피드 Re-ranking 규칙

**[초기안]**

- 최근 5개 중 동일 Primary Category 최대 3개
- 첫 5개 중 동일 Category 최대 2개
- 동일 작성자 연속 노출 금지
- 동일 Semantic Cluster 연속 노출 금지
- HIGH 연속 노출 제한
- RESTRICTED는 일반 첫 세션 제외
- Playful만 10개 연속 노출하지 않고 Practical·Discovery를 일부 혼합

## 30.2 유희 피로 방지

유희 비중을 높여도 다음 현상을 피한다.

- 모든 질문이 `평생 하나만` 포맷
- 음식·연애 질문만 반복
- 지나치게 유치한 문구
- 결과가 항상 90:10으로 끝남
- 사용자의 관심 주제와 무관한 가벼운 질문만 노출

## 30.3 Risk Budget

피드에는 카테고리 다양성뿐 아니라 Risk 상한을 둔다.

```text
신규 첫 세션
LOW 중심
MEDIUM 일부
HIGH 0
RESTRICTED 0
```

활성 회원에게도 HIGH·RESTRICTED가 Engagement만으로 연속 노출되지 않게 한다.

# 33. Taxonomy 버전 관리

## 33.1 코드 안정성

- 이미 사용한 코드를 다른 의미로 재사용하지 않는다.
- 표시명 변경은 가능하다.
- 삭제 대신 `DEPRECATED` 상태를 사용한다.
- Merge·Split 관계를 기록한다.

## 33.2 버전 예

```text
taxonomy_v2.0
quality_policy_v2.0
controversy_policy_v1.0
risk_policy_v2.0
```

각 Issue와 추천 Impression에 적용 버전을 기록한다.

## 33.3 Topic 승격·폐기

새로운 Free Tag가 충분한 재고와 사용자 행동을 가지면 Controlled Topic으로 승격할 수 있다.

폐기 기준:

- 의미가 중복됨
- 사용량이 매우 낮음
- 특정 단기 사건에만 해당
- 위험하거나 편향된 라벨
- 번역·지역 확장이 어려움

## 33.4 다국어

- 내부 코드는 언어 중립적으로 유지
- 표시명과 설명은 Locale별 관리
- 번역 과정에서 A/B 강도가 달라지면 별도 품질 검수
- 문화권에 따라 유희형 질문의 모욕 가능성 재검토

AI·편집 점수 구간별 실제 행동을 비교한다.

- 85점 이상
- 70~84점
- 55~69점
- 54점 이하

점수와 실제 반응이 일치하지 않으면 항목·배점을 조정한다.

# 부록 C. Quality Score 예시

## C.1 Playful Issue

```text
질문: 여행에서 하나만 포기해야 한다면?

B. 맛있는 음식
```

예시 평가:

|---|---:|

| 선택지 대칭성 | 15/15 |
| 중립성 | 15/15 |

주의: 실제 게시 시 기존 유사 질문 중복 여부를 확인한다.

```text
질문: 퇴근 후 업무 메신저에 응답하는 것도 업무의 일부라고 볼 수 있을까?
```

# 부록 D. Controversy 계산 예시

## D.1 저표본 50:50

```text
A 1표
B 1표
Balance Score = 1.00
```

그러나 Sample Confidence가 매우 낮으므로 논쟁 Feed 제외.

## D.2 Qualified 접전

```text
A 108표
B 92표
A Share = 54%
Balance Score = 0.92
정상 투표 = 200
Integrity = 정상
```

`QUALIFIED_CLOSE` 후보가 될 수 있다.

## D.3 초접전

```text
A 2,540표
B 2,460표
A Share = 50.8%
Balance Score = 0.984
정상 투표 = 5,000
Integrity = 정상
```

`VERY_CLOSE` 또는 `FEATURED_CLOSE` 후보.

## D.4 비율은 접전이나 무결성 이상

```text
A 51%
B 49%
최근 5분 신규 세션 98%
단일 Referrer 94%
Review Vote 급증
```

Balance가 높아도 Integrity Factor가 낮으므로 추천 중단·검토.

## D.5 댓글만 치열함

```text
A 78%
B 22%
댓글 수는 양쪽 비슷함
```

댓글 논의는 활발할 수 있지만 WHICH의 `논쟁` 정의에는 부합하지 않는다.

# 부록 F. 이번 문서의 결정 요약

## 확정

- 카테고리와 Risk는 분리한다.
- 하나의 Issue를 다축 Taxonomy로 분류한다.
- 초기에는 유희·가벼운 참여성 비중을 높인다.
- 유희성은 자극성·모욕성과 분리한다.
- 모든 Issue는 Experience Mode를 가진다.
- 정치·선거는 Fail-Closed RESTRICTED 검토를 적용한다.
- Quality·Safety Gate가 Engagement보다 우선한다.
- 논쟁은 A/B가 50:50에 가까운 접전이다.
- 논쟁 피드도 투표 전 정확한 결과를 숨긴다.
- 첫 정상 투표 후 질문과 A/B 의미를 변경하지 않는다.

## 설계 기준

- Universal Quality 80점 + Mode Fit 20점
- Playfulness Score 100점
- 첫 세션 유희 중심 Experience Mix
- Controversy Score에 표본·무결성·안정성·신선도 반영
- 동적 최소 표본과 Bayesian Smoothing 검토

## 초기안

- Active Pool Experience 비율
- 첫 10개 슬롯 구성
- Quality 80점 게시 기준
- 논쟁 등급별 50·200·500·1,000표 기준
- 45:55 접전, 48:52 초접전 라벨

## 미정

- 최종 관심사 카드 수
- 정확한 유희형 비율
- A/B 위치 랜덤화
- 논쟁 동적 임계값과 Stability 계산
- 정치 별도 논쟁 피드 여부
- 건강·법률·금융의 MVP 허용 범위
